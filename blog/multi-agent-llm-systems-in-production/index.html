Multi-Agent LLM Systems in Production: Four Safeguards

A multi-agent demo works when everything goes right. Production is about what happens when a model call hangs, a job retries, or a conversation runs long. These are the safeguards I added to FloatChat, and why each one matters.

01Why multi-agent demos break in production

Most multi-agent LLM demos are built for the happy path. A user asks a question, an orchestrator picks the right agent, the agent calls a tool, and a clean answer comes back. It looks finished. Then real traffic arrives.

In production, model APIs are sometimes slow. Background jobs retry. Conversations run for dozens of messages. Agents hand off to each other in ways nobody planned. None of these are rare edge cases; they are what normal operation looks like at volume. A system that only handles the happy path will eventually reply twice, stall a queue, run up a large bill, or say something nobody can explain.

This article walks through the safeguards I added to FloatChat, a self-hosted customer-support platform with a multi-agent AI layer. The specifics come from a Ruby on Rails system, but the ideas apply to any agentic AI stack, including Python ones.

02The system: FloatChat

FloatChat is a rebranded, self-hosted fork of Chatwoot 4.13, built on Rails 7.1, Vue 3, PostgreSQL and Redis with Sidekiq, and deployed with Docker. Customers write in over live chat, email, WhatsApp, social channels or SMS, and everything lands in one inbox.

The AI layer works like this:

01

A message arrives

The conversation sits in the pending (bot) state, waiting for the AI to respond.

02

A job is queued

A listener checks that the inbox has an AI assistant attached and queues the reply job on Sidekiq.

03

The orchestrator decides

An orchestrator assistant reads the conversation history and either answers or hands off to an admin-defined scenario agent.

04

Agents use tools

Seven built-in tools cover FAQ lookup, human handoff, resolving the conversation, private and contact notes, labels and priority.

05

Reply or hand off

The answer goes to the customer, or the conversation is passed to a person.

Every arrow in that flow is a place where something can go wrong. Four failures mattered most.

03Safeguard 1: a timeout on every model call

Agent runs happen inside background workers, and a worker handles one job at a time. If an LLM call hangs, the worker hangs with it. Every customer whose reply job is queued behind it waits too, even though their questions have nothing to do with the slow call.

The fix is an LLM timeout guard: a slow model call fails fast instead of stalling Sidekiq workers. A failed run is a much better outcome than a frozen queue, because a failure is visible and can be handled, while a hang quietly delays everyone.

The general rule for any agentic system is simple. Never call a model, or any external API, from a worker without an explicit timeout. Choose the number on purpose, based on how long you are willing to make a customer wait, not on a library default.

04Safeguard 2: make every run safe to retry

Background jobs retry; Sidekiq, for example, retries failed jobs automatically. That is a feature: if a worker crashes or a network call fails, the job runs again and the customer still gets an answer. But an agent run is not a pure function. By the time it fails, it may already have posted a reply, added a label or written a private note.

Run the same job again and you can get a duplicate reply, or the same tool action twice. For a customer, two identical answers look broken. For the support team, repeated labels and notes make the conversation history harder to trust.

FloatChat uses a Redis run registry that tracks each agent run and prevents duplicate replies and repeated tool actions. In general terms this is idempotency: a retry should recognise work that is already done and skip it, rather than doing it again. If you are building this yourself, the pattern is:

  • Give each run a stable identity, so a retry is recognised as the same run.
  • Record side effects such as replies and tool actions as they happen, not only at the end.
  • Check that record before acting, so a retry only does what is still missing.

05Safeguard 3: hard limits on handoffs, tool calls and history

Agents that can hand off to each other can also loop. An orchestrator passes to a scenario agent, which decides the question belongs elsewhere and passes it back. Tool calls can repeat in the same way. Meanwhile, every message in a long conversation adds to the context sent to the model, which raises cost and latency and eventually hits the context window.

FloatChat caps every run at 8 handoffs, 12 tool calls and 30 messages of history, and truncates long messages before they reach the model.

Hard limits do two things. They make the worst case predictable: you know the maximum number of model calls one customer message can trigger, so you know the maximum cost and roughly the maximum time. And they turn an endless loop into an ordinary failure that can be handled like any other, usually by handing the conversation to a person.

The exact numbers matter less than the fact that they exist and were chosen deliberately. Start with limits that comfortably cover your real conversations, then watch the logs to see whether runs ever hit them.

06Safeguard 4: log every run

When a customer gets a strange answer, someone will ask why. "The model decided" is not an explanation anyone can act on. To answer the question you need to know which agent handled the conversation, which tools it called, what came back, and where it handed off.

FloatChat records every agent run with a run logger, for tracing and debugging. That turns a bad reply from a mystery into something you can trace back to the step that caused it, whether that was a missing FAQ entry, a poor handoff decision or a tool returning the wrong thing.

Logs also tell you whether the other safeguards are working. If runs regularly hit the handoff limit, the scenario agents need clearer boundaries. If timeouts fire often, the model or provider may be the problem.

07Always leave a way out to a human

The safeguards above keep the system stable. They do not make the AI right every time, so the most important tool an agent has is the one that stops it: human handoff.

In FloatChat, when the AI cannot help, the conversation leaves bot mode, gets an activity note explaining what happened, and is auto-assigned to a human agent with free capacity. The customer is never stuck talking to a bot that has run out of answers, and the person who picks it up can see why it arrived.

Design the handoff as a first-class path, not an error case. It should be fast, it should carry context, and it should be the default whenever the AI is unsure.

08Let it learn, but review what it learns

FloatChat mines resolved conversations for new FAQ entries, which is how the knowledge base keeps up with what customers actually ask. Left unchecked, that loop could also teach the system its own mistakes: a wrong answer that happened to close a conversation would become a new FAQ.

So new entries are saved as pending for review rather than going live, and they are de-duplicated against the approved ones. The system proposes; a person approves. It is a small step that keeps a self-improving system from drifting.

09Keep the model a configuration choice

Models change quickly, and the best one for a task today may not be the best in six months. In FloatChat the model, provider and temperature are set per assistant, with GPT-4.1 as the default and provider mapping for OpenAI, Anthropic, Google, Mistral and DeepSeek.

Treating the model as configuration rather than code means you can try a new one on a single assistant, compare the results, and switch without a deploy. The safeguards stay the same whichever model sits underneath.

10A production checklist for multi-agent LLM systems

  • Put an explicit timeout on every model and API call made from a worker.
  • Make agent runs safe to retry, so a retry never repeats a reply or a tool action.
  • Cap handoffs, tool calls and conversation history per run, and choose the numbers on purpose.
  • Log every run so any reply can be traced back to the steps that produced it.
  • Make human handoff fast, automatic and full of context.
  • Review anything the system learns before it goes live.
  • Keep the model and provider configurable per assistant.
