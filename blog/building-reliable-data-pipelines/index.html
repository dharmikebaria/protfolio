From ETL to Insight: Building Reliable Data Pipelines

A data pipeline is only useful if people trust the number at the end of it. This is how I built an ETL pipeline that joins GA4 data in BigQuery with Google Ads spend, and what made it reliable enough to act on.

01A question split across two systems

The marketing team had a simple question: what do our paid campaigns actually deliver? The answer was split across two systems. Ad spend lived in Google Ads. Conversions and user behaviour lived in GA4.

Comparing the two meant manual exports and spreadsheets. Spend was downloaded from one tool, conversions from the other, and the numbers were lined up by hand. It worked, slowly, and nobody was fully sure the numbers matched. Campaign decisions were slow and hard to trust.

The GA4 Paid Traffic Dashboard replaced that process with an ETL data pipeline. This article covers how it is built and, more importantly, what made it reliable enough that people acted on its numbers.

02Why manual exports are not a pipeline

Manual exports fail in predictable ways. Date ranges drift between the two downloads. A filter is applied in one tool and not the other. A spreadsheet formula is copied one row short. Each mistake is small, but together they make every number arguable, and an arguable number does not get used.

A data pipeline fixes this by making each step the same every time. The extraction uses the same query, the join uses the same keys, and the output arrives on the same schedule. The goal is not only speed. It is consistency, because consistency is what earns trust.

03The architecture, step by step

01

Extract GA4 events from BigQuery

GA4 events are exported daily into date-partitioned tables in Google BigQuery, and the event data is queried there directly with SQL.

02

Select the right partitions

Parameterised table IDs pick the partitions for any reporting window, so the same query serves any date range.

03

Extract spend from the Google Ads API

Campaign spend is fetched through the Google Ads API instead of a manual export.

04

Join and compute

Events and spend are combined to measure performance per campaign.

05

Serve and schedule

Results are served through a Django REST Framework backend backed by PostgreSQL, and reports are emailed on a schedule by APScheduler.

The stack is deliberately ordinary: Python, SQL, BigQuery, the Google Ads API, PostgreSQL, Django REST Framework and APScheduler. Reliability came from how the pieces were used, not from exotic tools.

04Querying GA4 data in BigQuery for any date range

The GA4 BigQuery export writes one table per day, with the date as a suffix in the table name. That is efficient, because a query only needs to scan the days it covers. It also invites a bad habit: hard-coding dates into queries, then editing them by hand every time someone wants a different window.

It also matters for cost. Under BigQuery's on-demand pricing, you are charged for the bytes a query processes, so a query that reads every day of history to answer a question about last week is slower and more expensive than it needs to be.

The pipeline parameterises the table IDs instead, so the right partitions are selected automatically for any reporting window. Nobody edits SQL to change a date range, which removes a whole class of copy-and-paste mistakes.

As an illustration of the general technique (not the production query), BigQuery lets you query all the daily tables with a wildcard and filter them by suffix using parameters:

SELECT event_name, COUNT(*) AS events
FROM `my-project.analytics_123456.events_*`
WHERE _TABLE_SUFFIX BETWEEN @start_date AND @end_date
GROUP BY event_name
ORDER BY events DESC;

Because the date range is a parameter, the same query can power a daily report, a monthly review and a one-off question, and BigQuery only scans the tables inside the range.

05Validate the join before you trust the join

Joining ad spend to on-site behaviour depends on the tracking that links an ad click to a GA4 session. That link comes from the GCLID, the click identifier Google Ads adds to ad URLs through auto-tagging, and from UTM parameters that tag the campaign, source and medium.

That tracking was unreliable. When the keys connecting two datasets are wrong, every metric built on the join is wrong too, and no amount of clever SQL downstream can fix it.

So before building on the join, I validated GCLID and UTM tracking using statistical analysis and A/B testing, reaching 100% data accuracy. It was the least visible part of the project and the most important one, because everything the dashboard reports depends on it.

The general lesson: when a pipeline combines sources, check the keys first. Count how many records match, how many do not, and why. A join that silently drops or duplicates rows is one of the most common ways a pipeline produces confident, wrong numbers.

06Serve the data, then take people out of delivery

Once the numbers are right, they need to reach people. The results are served through a Django REST Framework backend with PostgreSQL, which gives the dashboards a stable API instead of a folder of files.

Then there is delivery. A report that depends on someone remembering to run it is not really a pipeline; it is a manual task with extra steps. APScheduler sends reports by email on a schedule, so the numbers arrive without anyone pulling them.

An API also gives every consumer the same numbers. When three people each open their own copy of an export, they end up with three slightly different versions of the truth. When everyone reads from one endpoint, a correction made once reaches everyone.

Across the BI dashboards I worked on there, time-to-insight fell by 70%.

07Habits that keep any data pipeline trustworthy

Beyond the specifics of GA4 and Google Ads, a few general habits separate pipelines people trust from pipelines people double-check. None of them are complicated; they are mostly about being able to answer "is this number right?" quickly.

01

Make loads safe to re-run

If a day's load fails halfway, running it again should replace that day's data, not add a second copy. Pipelines that append blindly turn every retry into a duplicate.

02

Keep raw data separate from results

Store what came out of the source unchanged, and build the transformed tables from it. When a calculation turns out to be wrong, you can fix it and rebuild instead of re-extracting everything.

03

Watch freshness and volume

A simple daily check that the latest data arrived, and that the row count is in a normal range, catches most silent failures before a stakeholder does.

04

Write down what each metric means

Agree on definitions such as what counts as a conversion and which date a cost belongs to. Many arguments about numbers are really arguments about definitions.

Each of these is cheap to add at the start and expensive to retrofit once people depend on the output.

08The same pattern with a messier source

The sources change, but the shape of the pipeline does not. At Jolly Clamps, the inputs are not APIs but daily Excel exports from the ERP and production-planning systems: dispatch, lead time, MPS / MTO schedules and forecast demand.

Excel exports are harder to work with than APIs, because every export type has its own layout. The ERP Data Automation Portal handles this with a reusable openpyxl parser library that maps each export into a consistent data model. Parsed data is stored in structured PostgreSQL models through Django REST Framework, teams use a React portal instead of passing spreadsheets around, and recurring production and dispatch reports are generated automatically with Google Apps Script.

The principle is the same as with GA4: deal with the mess once, at the edge of the system, and give everything downstream one clean, predictable shape.

09A checklist for reliable ETL pipelines

  • Start from the question the team is asking, then find where each half of the answer lives.
  • Check the keys that link your sources before building anything on the join.
  • Parameterise date ranges and table names, so nobody edits a query by hand.
  • Map messy inputs into one consistent data model as early as possible.
  • Serve results through an API, not a folder of exports.
  • Automate delivery, so the pipeline does not depend on anyone remembering to run it.
