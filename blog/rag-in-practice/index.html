RAG in Practice: Grounding LLMs in Your Own Data

A language model knows a lot about the world and nothing about your business. Retrieval-augmented generation closes that gap. Here is how RAG works in the chatbots I have built, including the ones that talk.

01The problem with generic answers

A large language model knows a lot about the world and nothing about your business. Ask it about a brand's return policy, opening hours or product range and it will produce a fluent answer anyway. Sometimes that answer is right. Often it is a plausible guess, and a customer cannot tell the difference.

That was the problem with the client chatbots I worked on: brands needed bots that answer from their own content, not generic LLM guesses. Retrieval-augmented generation, or RAG, is how we solved it.

This article explains how RAG works in practice, using two systems I have built: a RAG Voice Chat System deployed across multiple client brands, and the knowledge base inside FloatChat, a self-hosted support platform.

02What retrieval-augmented generation actually does

RAG changes where the answer comes from. Instead of asking the model what it knows, you first search your own content for passages relevant to the question, then give those passages to the model and ask it to answer from them.

01

Prepare the knowledge

The brand's own content becomes the chatbot's knowledge source.

02

Retrieve

For every question, the most relevant passages are retrieved from that content.

03

Generate a grounded answer

The model answers using only the retrieved passages.

The model still does the writing, but it is no longer the source of the facts. That is the whole idea, and most of the engineering is in making each of those three steps good.

03Step one: the knowledge base decides the quality

It is tempting to focus on the model, but answer quality is mostly decided before the model is involved. If the right information is missing from the knowledge base, or buried in a long page that never gets retrieved, no model can answer correctly.

FloatChat takes a structured approach. Crawled websites and uploaded PDFs are turned into question-and-answer pairs rather than stored as raw pages. A customer question is then matched against questions the knowledge base already answers, which tends to be a cleaner match than searching long documents.

Whatever format you choose, treat the knowledge base as a product: keep it accurate, remove outdated entries, and add what customers actually ask about.

04Step two: embeddings and vector search with pgvector

To find relevant entries, each one is converted into an embedding: a list of numbers that represents its meaning. Questions with similar meanings end up with similar embeddings even when they use different words, so "Can I send it back?" can match an entry about returns.

In FloatChat, entries are embedded with OpenAI's text-embedding-3-small model and stored in PostgreSQL using pgvector, as 1536-dimension vectors searched by cosine similarity. Keeping the vectors in PostgreSQL means the knowledge base lives next to the rest of the application data, with no separate vector database to run.

As a general illustration (not FloatChat's actual query), a pgvector similarity search looks like this, where <=> is pgvector's cosine distance operator:

SELECT question, answer
FROM faq_entries
ORDER BY embedding <=> $1
LIMIT 5;

The application embeds the customer's question, passes that vector in as $1, and gets back the closest entries. Those entries become the context the model answers from.

05Step three: answer from the context, and only the context

The final step is to give the model the retrieved passages and the question, with a clear instruction to answer only from what was provided. The instruction matters: without it, the model will happily fill gaps from general knowledge, which is exactly what RAG is meant to prevent.

In FloatChat this happens through an FAQ lookup tool. The agent searches the knowledge base, reads what comes back, and answers from it.

06When retrieval finds nothing

Every RAG system meets questions its knowledge base cannot answer. What happens next is a design decision, and the worst option is to let the model improvise.

In FloatChat, when the AI cannot answer from the knowledge base, the conversation is handed to a human: it leaves bot mode, gets an activity note, and is auto-assigned to an agent with free capacity. A customer who reaches a person is far better served than one who receives a confident wrong answer.

Those unanswered questions are useful signals too. FloatChat mines resolved conversations for new FAQ entries, saves them as pending for review and de-duplicates them against approved ones, so the knowledge base grows from real gaps rather than guesses.

07Adding a voice

In the RAG Voice Chat System, people can talk instead of type. Real-time transcription turns speech into text, the RAG pipeline produces a grounded answer, and ElevenLabs turns that answer into natural voice.

Voice raises the stakes on accuracy. On screen, a reader can skim a reply and notice something odd. A spoken answer sounds equally confident whether it is right or wrong, and the listener has fewer cues to question it. Grounding matters even more when the output is a voice.

08One stack, many brands

The second challenge was scale: serving many brands without rebuilding a chatbot each time. The answer was one reusable stack, configured and deployed per brand. The retrieval, generation and voice pieces stay the same; only the knowledge and configuration change.

That stack now sits behind 10+ AI chatbots for 8+ client brands. Alongside it, Vapi.ai is configured for outbound voice-AI outreach across 4 countries.

Treating each brand as configuration rather than a fork is what keeps this manageable. A fix or improvement lands once and reaches every brand.

09Common RAG mistakes to avoid

Most RAG systems that disappoint fail in the same few ways. These are general patterns worth checking in any retrieval-augmented generation project, whatever stack it uses.

01

Chunks that are too big or too small

If you split documents into chunks, very large chunks bury the relevant sentence among unrelated text, and very small ones lose the context needed to understand it. Chunks should each answer something on their own.

02

Retrieving too much

Passing a dozen loosely related passages to the model makes it harder, not easier, to find the right answer. A few highly relevant passages usually beat many mediocre ones.

03

Mixing knowledge that should be separate

In a multi-tenant system, one brand's chatbot must never retrieve another brand's content. Keep each knowledge base clearly scoped, and filter by it on every search.

04

Letting content go stale

A knowledge base that was accurate at launch drifts as policies, prices and products change. Retrieval will faithfully return outdated answers unless someone keeps the content current.

10How to test a RAG system

It is hard to improve what you do not measure, and RAG systems are easy to judge by gut feel. A light, repeatable test set works better.

Collect a set of real questions, ideally from actual customer conversations, along with what a correct answer should contain. Then check two things separately. First, retrieval: for each question, did the right entry appear in the results? Second, generation: given the right entry, did the model produce a correct, grounded answer?

Separating the two tells you where to spend effort. If retrieval misses, improve the content or the search. If retrieval is right but answers are wrong, improve the instructions or the model. Re-run the same set after every change, so you know whether it helped.

11A RAG checklist

  • Treat the knowledge base as the product. Retrieval cannot fix content that is missing or wrong.
  • Structure content so it matches the questions people actually ask.
  • Use embeddings to match on meaning, and keep vectors close to your data where you can, for example with pgvector.
  • Tell the model to answer only from what was retrieved.
  • Decide what happens when retrieval finds nothing, and prefer a human handoff to a guess.
  • Review anything the system learns before it goes live.
  • Build the pipeline once and make each brand a configuration, not a fork.
